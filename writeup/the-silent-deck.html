The Silent Deck

Teaching an Ajazz AKP153E to talk to flight sim mission software, told from both sides of the keyboard.

Why there was a deadline

A colleague is leaving. He has been building a C# application for IL-2 Korea that plans missions and uses AI to generate them, and next week is his last. The stream deck and the source code that drives it are a leaving gift, which is the only reason any of this happened on a schedule.

That set the brief. A planner tells you what a mission should be. Running one live means deciding what happens next while people are already in the air, so the deck had to work as a control surface for the person orchestrating a session rather than the person flying in it. Closer to a game master's screen than a cockpit.

Tyson

Fifteen keys within reach, labelled, with no menus and nothing that requires alt-tabbing out of a full screen simulator. That constraint is what makes the hardware worth the integration work. Anything you can comfortably do with a mouse did not need a deck in the first place.

01

Easy to open, impossible to talk to

The deck was an impulse buy that had finally found a use. Plugged in, it enumerated as something promising: a vendor defined HID device on usage page 0xFFA0, bound to Microsoft's stock HidUsb driver. No vendor SDK, no signed driver, no kernel work. Just 513 byte reports in both directions and no documentation about what to put in them.

It also brought a second USB device along, a mass storage sibling for its internal image store. It was a red herring.

Tyson

I have spent a few years on MAVLink, sensor payloads and vehicle control brokers, so the shape of this was familiar: an undocumented wire protocol riding a transport I already trust. That is not a mystery, it is just work.

02

Three probes, none of which worked

The machine had .NET runtimes but no SDK, so nothing could be compiled yet. The first move was a PowerShell script calling into hid.dll directly, just to read the device's capabilities and listen for a keypress.

It failed three times in a row, and each failure was a different mistake. A shell heredoc quietly ate the backslashes out of the device path, so the first two runs died on ERROR_PATH_NOT_FOUND and then ERROR_BAD_PATHNAME. The third opened the device correctly, read its capabilities, and then crashed because the capture loop was a PowerShell script block running on a raw .NET thread, which is not a thing that works.

The fourth attempt did not crash. It hung. That hang turned out to be the most useful result of the three.

Tyson

Three failures, three unrelated causes, and none of them the device. This is the stage where it gets tempting to start theorising about the hardware, and there was nothing yet to theorise with. A path error, a threading mistake and a blocking call tell you about your harness, not your target. Tooling you cannot trust produces evidence you cannot use.

Claude

The sequencing error was mine. I asked for keypresses before verifying that anything was reading them, and a person at the hardware is the one resource I cannot supply for myself. Verify the listener first, then ask for input.

The hang was diagnostic because of why it hung. CloseHandle blocks while a synchronous HID read is still pending, and a HID read only completes when a report arrives. The process could not exit, which meant no report had arrived, which meant the silence was real and not a parsing mistake. A bug had accidentally answered a question.

03

Stop guessing, start instrumenting

At that point the throwaway scripts were retired, the .NET 8 SDK went on, and the work moved into a real project: overlapped I/O so reads could time out cleanly instead of blocking forever, and a heartbeat that reported what the read loop was actually doing.

That heartbeat settled the question that had been costing the most time. Was the device silent, or was our reader broken?

Claude

This line should have existed before any probing started. Until it did, every failure had two possible explanations and the choice between them was intuition. One counter turned an argument into a fact.

04

Half the integration was already working

If input was dead, output was worth testing separately. A brightness command went down the wire three times in a row, dark to bright, while someone watched the hardware.

Tyson

"Yeah, it's blinking." Which was more informative than it sounds. The device was right, the interface was right, the report framing was right, the 513 byte packets with the ASCII CRT header were right. Everything about the write path was correct while the read path returned nothing whatsoever. That asymmetry is what told us this was a state problem rather than a protocol problem.

05

A key that switched off its own screen

The observation that broke the deadlock did not come from a debugger.

Tyson

I pressed a key and the panel turned its own screen off. Press again, back on. That is standalone firmware behaviour. No host had claimed the device, so it fell back to running its own screen. I have met the same pattern in marine sensor integrations often enough: the hardware sits there perfectly functional and perfectly useless until the host says the specific thing it is waiting to hear.

Claude

I had been treating the silence as something wrong with my code. That single sentence reframed it as something correct about the device. Different problem, different search.

The most valuable diagnostic in the whole exercise was a person looking at the hardware and describing what it did.

06

Reading someone else's homework

Tyson

I had gone looking for open source drivers for this device before any code was written, so I knew prior art existed and said so early: use it as reference, this is a personal project, there is no reason to derive the protocol from first principles. Somebody had already paid that cost in public.

That prior research is what made the next step productive. This device family has been reverse engineered before, in the open. Four independent sources documented the protocol: the command header, the ASCII verbs, the fact that input reports arrive prefixed with ACK, and that the key number sits at byte 9 of the payload.

We had already tried the two commands that look like handshakes, DIS and CONNECT. Both were accepted. Neither produced a single keypress. The answer was not in the protocol documentation at all. It was in what a working implementation happened to do at connect time: set brightness, clear every key, flush. Three commands that all read as cosmetic.

We sent that sequence. Keys started streaming immediately.

Claude

Worth being precise about what open source contributed here. It did not hand over the answer. Nobody's README says "the device stays mute until you clear the keys." What it did was narrow the search from the entire space of possible USB behaviour down to one file, where the initialisation order was sitting in plain sight. Reading it was quick. Deriving the same answer unaided would not have been.

07

Fifteen keys, numbered from the right

With input flowing, the mapping fell out of one deliberate test: press all fifteen keys in reading order and write down what the hardware reports.

The answer was 13 10 7 4 1, then 14 11 8 5 2, then 15 12 9 6 3. The deck numbers its keys column by column starting from the right, so hardware key 1 is the top right corner and 13 is the top left. Rather than expose that to anyone else, the library translates it to reading order and keeps the convention to itself.

Tyson

Worth noticing what that ordering actually is. Fill the rightmost column top to bottom, then step one column left. That is traditional vertical CJK column order, the direction Chinese and Japanese text ran before horizontal left to right became the norm. Whether the firmware author had writing direction in mind or was simply following the key matrix, I have no way to know from out here, and it would not have changed the test either way. Plausible explanations are not measurements.

The same test settled a constraint worth knowing early. This protocol revision sends a single event per press, with no separate down and up transition. Hold duration is therefore unmeasurable, which makes long press gestures impossible on this hardware rather than merely unimplemented.

08

Eight orientations at once

Key images are 85 by 85 JPEGs, and the panel rotates and mirrors whatever it is given. The documentation described the transform as "rotate 90 degrees and mirror both axes," which is a real transform but an awkward way to write one.

Testing that serially would have meant a guess, a photo, a correction, repeat. So instead all eight possible orientations went to eight different keys in a single pass, each stamped with a letter F and a corner marker. One photograph identified the winner: rotate 270, no mirroring.

The same photograph exposed a second bug for free. The images had landed in the wrong columns, which meant image slots use the same right to left hardware numbering as key input, and the code had been passing reading order. Decoding which colour sat on which key gave both answers from one round trip.

09

From driver to something usable

The work then split into four projects with one deliberate boundary between them. The hardware layer knows about HID and nothing else. A core library holds profiles, pages, rendering and dispatch with no UI reference at all, so the runtime that drives the deck during a mission does not depend on the editor existing. A WPF application edits profiles. A console tool does diagnostics.

The editor's preview is drawn by the same renderer that paints the hardware, so the screen shows the deck's own output rather than an approximation of it. Press a physical key and the editor selects it.

The GUI bugs were more ordinary than the protocol ones: white text on a white dropdown, colour swatches that repainted themselves grey on hover because a general button style overrode their fill, and a stale binding that kept drawing RESERVED badges on keys that were no longer reserved. That last one was the only interesting failure of the three, because the display was confidently telling the user something untrue about the state of the system.

10

What it looks like finished

The editor opens with the flight sim profile loaded: seven pages down the left, the deck face in the middle, and the properties of whichever key is selected on the right. Selecting the Compass key shows its label, its Target glyph, its background as a hex value with a palette of thirty nine swatches under it, and the event name Nav.Compass that the host application will receive when the key is pressed. A status line at the bottom reports where the profile was saved.

The deck face in the editor and the deck face on the desk are the same picture, because the preview is drawn by the renderer that paints the hardware. There is no second design language to keep in sync and no round trip to the device to find out what a key will look like.

Tyson

Editing is live. Type in the label field and the key changes under your hand, and pressing a physical key selects it in the editor, which is how you label fifteen keys without counting rows to work out which one you are on. The labels on this page are shorter than the ones I first wrote. Prev WP and ALT started out as Prev Waypoint and Altimeter, and the deck told me immediately that they were too long.

Two things the hardware knows that the preview does not.

The panel does not show the whole 85 by 85 image. A few pixels around the edge sit under the plastic bezel, so a label pushed to the bottom of the tile gets its descenders trimmed on the device while sitting comfortably in the preview. Content needs a safe margin, and the preview should be drawing that margin too.

Dark backgrounds also refuse to stay dark. The keys are lit from behind, so a near black tile reads as mid grey on the panel while the saturated colours come through accurately. On this hardware colour carries the information and brightness does not, which is worth knowing before designing a palette around dark neutrals.

The sixth column, the narrow strip to the right of the keys, stays blank. It is not a button, nothing addresses it yet, and the reference material describes this device family as having three positions there that are not keys.

What broke, and what fixed it

What we read

None of these projects target this use case, and none are in C#. They were valuable as protocol references, which is exactly what open source is for.

  • Uriziel01 / Ajazz-AKP153-reverse-engineering Clean room notes on the packet structure and command headers.
  • 4ndv / mirajazz A Rust library for this device family. The clearest implementation of the wire format.
  • 4ndv / opendeck-akp153 Where the initialisation order was hiding, and the confirmation of protocol revision and key count.
  • ZCube's protocol notes Byte offsets for key reports and the image upload sequence.
Tyson

The language was incidental

The language was never the interesting part of this. P/Invoke against hid.dll is the same conversation as any other foreign function interface, and WPF is a layout engine with opinions. What mattered was the method: isolate the transport, prove one direction before blaming the other, instrument instead of theorising, and read the people who already solved it.

That transfers. It is the same loop as bringing up an unfamiliar payload on a vehicle, and it does not much care what the payload is or which language the host is written in. The deck goes out next week with the source.

Claude

Access was the limit, not reasoning

I read the four protocol references, wrote the HID layer and spotted the initialisation order buried inside one of them. I was reading them because Tyson had already scouted the open source landscape and directed the work there. My own failures were in the tooling, and in assuming the silence was a defect in my code rather than documented behaviour of the device.

Both turning points came from the other side of the desk: a screen toggling on keypress, and a photograph of coloured keys that decoded two problems at once. I can read an unfamiliar codebase quickly. I cannot look at the hardware.
